## 轮次详解

### 2026-10-10 · 首轮

**成果：成功 8 条，全部在 4 店。**

```
4店： 参加位 16（8 成功 / 8 弹窗复核后取消），跳过 175
      （无绿字 136、无激活 19、净收不高于基准 20）
10店：参加位 3（全部弹窗复核取消），跳过 150
```

**这轮最重要的发现：「优化折扣」13 条全军覆没。**

13 条 opt 提案，弹窗里全都是「新提案 < 当前」，全部取消。

当时的判断是"这是市场行情"——平台不会持续给你更好的提案。这个判断后来被证明**只对了一半**（见 10-17）。

**首次验证「弹窗二次复核」有效**：拦下 1 条（某档弹窗 30.09 < 基准 33.19）。
如果没有这道复核，它会以「成功」记录，实际是亏的。

**首次确认 `--cols-1` 陷阱处理正确**：两条 `structured_single` 读数正确。

### 2026-10-11 · 成功的全是「立即参与」

**成果：成功 4 条（4 店 3 / 10 店 1）。**

```
4店： 参加位 11（3 成功 / 8 取消），跳过 185
10店：参加位 4（1 成功 / 3 取消），跳过 144
```

**观察：4 条成功全部是「立即参与」，其中 2 条是限时抢购。**

这条观察开始形成一个假设：**价值集中在新增提案侧，优化侧长期无收益**。

这个假设很危险——如果当时据此把 opt 入口关掉，10-17 那次破冰就不会发生。

**「优化折扣」连续第二轮零通过**（11 条取消全是新提案 < 当前）。

### 2026-10-14 · 两个事故

这轮是全项目最糟的一天。

**事故一：10 店掉登录**

```
10店：0 条
```

日志干干净净，就是「第1页无组」。页面实际停在：

```
www.mercadolivre.com.br/login/identification?challenge_id=…
```

要求输邮箱 + reCAPTCHA。

尝试恢复：

- `close_store` → `open_store`（reused=false 全新开）→ **仍是登录页**
- 结论：必须人工在紫鸟重登

**事故二：结果 JSON 永久丢失**

为了排查 10 店，追加跑了 `--store 10店 --dry`。

然后发现：**`--dry` 同样会覆盖 `tmp/auto_join_promos.json`。**

更糟的是恢复时拿错了备份文件——「跑前备份」实际是 10-13 的旧文件。
拷回去之后，10-14 这一轮的完整结果彻底没了。

**由此产生三条铁律：**

1. 排查一律先 `cp` 当前结果到带时间戳的新备份，**并核对备份里的 ts 确实是上一轮**；
2. 绝不用 `--dry` 做复核；
3. 复盘优先读 stdout 日志。

现在 `main.py` 的 `backup_previous_result()` 用**旧文件内部的 ts** 做备份名，
就是为了解决「文件名带的是当前时间、分不清是哪一轮」这个问题。

**4 店这轮正常**：143 条 → 成功 3 / 待核验 2 / 失败 1 / 优化取消 8。

其中：

- `PET-BAG-55375-GY` 114.29 > 110.37 数量 12，**点确认后无任何 snackbar** → 待核验；
- `PB-20K45-SKI` 123.73 > 123.3，平台回执「我们未能将您的发布添加到促销中。请重试」→ **实为失败**；
- `GDSZAL200A` 334.73 > 331.89，确认按钮不可用 → 失败。

**「待核验」和「失败」的区别在这里体现得很清楚**：
前者动作发出去了没回执，后者平台明确拒绝。

### 2026-10-17 · 4 店掉登录 + 优化折扣破冰

这轮同时出现了「最坏」和「最好」两件事。

**坏消息：4 店掉登录，整店 0 条。**

```text
🔴 第1页无组，结束分页
href : https://www.mercadolivre.com.br/login/identification?challenge_id=…
title: Digite seu e-mail ou telefone para iniciar sessão
```

`store open`（reused=true）后连访 3 次仍是登录页 → 必须人工重登。

**这次轮到 4 店**——10-14 是 10 店。所以：

> 掉登录会在两店之间**轮换出现**，不能预设「只有某个店会掉」。

**好消息：10 店成功 5 条，其中包含「优化折扣」破冰。**

```
10店：参加位 11（5 成功 / 4 优化取消 / 1 失败 / 1 待核验），跳过 126
```

5 条成功里有一条是：

> **`NY-37295-BE` 优化折扣 40.28 > 38.83 —— 连续 8 轮零通过后首次「优化折扣」通过**

**这条是整个项目最重要的实证之一。**

它证明：opt 入口的正确率高但不常开。8 轮零通过不是「入口坏了」，
而是「行情确实没那么好」。如果因为长期零通过就关掉它，就会错过这一条。

**另一条观察：本轮 0 条限时抢购参加。**

全量 15 张卡片含限时抢购关键字，但全被前置条件（无绿字 / 净收不达标）拦下。
这说明限时抢购不是稳定来源——往轮常见 5～7 条，这轮 0 条。

## 从九轮里提炼出的六条结论

### 1. 「优化折扣」不能因为长期零通过就关掉

8 轮零通过 → 第 9 轮破冰。

**证据**：10-17 `NY-37295-BE` 40.28 > 38.83。

**推论**：低频率高价值的入口，不能用「近期通过率」来判断它的价值。
判断标准应该是「单条通过时的收益 × 通过概率」，而不是「最近有没有通过」。

### 2. 掉登录是最高频的假故障，且会在两店之间轮换

| 日期 | 掉的店 |
|---|---|
| 10-14 | 10 店 |
| 10-17 | 4 店 |

**推论**：任意一店 0 条都先查登录态。已写进 `main.py` 的强制检查。

### 3. 净收不达标取消是常态，不是异常

每轮有 7～10 条提案在弹窗复核时被取消。这是**机制在正常工作**——
说明卡片上的净收和弹窗里的最终净收确实会不一致。

如果哪天这个数字变成 0，反而要怀疑复核逻辑是否失效了。

### 4. 真实成功率约 2%～5%

| 指标 | 数值 |
|---|---|
| 单轮判定记录 | 137～347 |
| 单轮真实参加 | 3～9 |
| 参加占比 | 约 2%～4% |

**大部分提案是不值得参加的。** 这正是自动化的价值——
人工不可能每天盯着 300 条提案做 2% 的筛选，而且漏判成本很高。

### 5. 耗时主要花在展开，不可能压缩到分钟级

20～35 分钟，其中 15～30 分钟是「每组独占一次 reload」。
这是平台行为决定的，见 [05_Expand_Rule.md](05_Expand_Rule.md)。

### 6. 业务信号要能从日志里读出来

「10 店无激活从 20 涨到 40」这个信号，只有连续记录才能看出来。
单轮跑完看到「跳过 129」是没有信息量的。

**所以结果 JSON 必须保留每一条跳过的原因**，而不是只统计成功数。
这正是 `summary.跳过原因Top` 存在的意义。

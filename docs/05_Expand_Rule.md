# 05 · 展开铁律：一次页面加载只能展开一次

## 结论先行

> **同一次页面加载里，只有第一次「展开」点击有效。第二次起，点击一律不生效。**

不接受任何「多等一会儿」「多重试几次」的解法。唯一可行的做法是：
**每个需要展开的商品组，独占一次页面加载。**

这不是一个可以绕过的小毛病，它是这个项目 20～35 分钟耗时的主要来源。
理解它，才能理解为什么脚本要反复 reload。

---

## 现象与排查过程

### 初次观察

展开第 1 个组 → 正常，子行出现。
展开第 2 个组 → 点击后行数恒为 1，看起来像「没展开」。

### 排除的可能

| 猜测 | 验证 | 结论 |
|---|---|---|
| 点击没生效（CDP 问题） | 检查按钮是否拿到点击事件 | 点击确实到达了元素 |
| 页面还没渲染完 | 加长等待到 30s | 无效，行数始终是 1 |
| 后台标签页冻结 rAF | 检查 `document.visibilityState` | 是 `visible`，与它无关 |
| 元素不在视口 | 先 `scrollIntoView` 再点 | 仍然无效 |

### 定位

关键实验：**reload 一次页面，然后展开同一个组** → 成功。

再实验：**在已经展开了第 1 个组的页面上，reload，然后展开第 2 个组** → 成功。

结论：**限制是按「页面加载次数」计的，不是按组、不是按时间。**
每次页面加载，展开能力只有「一次」的配额。

### 为什么平台会这样

推测是列表组件在首次展开时建立了某种内部索引（子行是懒加载的，首次展开才向服务端拉子行数据）。
这个索引只在首次展开时初始化，后续展开请求因为索引已「用过」而被静默丢弃。
**平台不报错，只是不响应**——这也是为什么它如此难排查。

## 实现

```python
def expand_fresh(store, page_url, prefix, tries=3):
    for t in range(tries):
        L.visit(store, page_url, wait=13)          # ← 关键：每次展开前 reload

        gi = group_index_by_prefix(store, prefix)  # ← reload 后索引会漂移，必须重定位
        if gi is None:
            print("[warn] reload 后找不到组「%s」，重试" % prefix[:24])
            continue

        L.exec_js(store, EXPAND_ONE % gi)          # 给箭头打标记
        L.click(store, '[data-ajchev="1"]')        # CDP 真实点击

        for _ in range(8):                         # 轮询子行是否出现
            time.sleep(4)
            g = group_at(store, gi)
            if g and len(g.get("rows") or []) > 1:
                time.sleep(1)                      # 让卡片渲染完
                return group_at(store, gi) or g

        print("第%d次展开 gi%d 未出子行，重试" % (t + 1, gi))
    return None
```

### 两个不能省的细节

**① reload 后必须重新定位 gi**

组顺序会漂移。平台插入广告位、活动状态变化（激活→已预约）都会改变排序。
展开前记下的 `gi` 在新页面上可能指向**另一个商品**——这时候点展开，
展开的是别人的组，而你以为在处理目标商品。

定位用的是 `norm_title` 归一后的标题前缀：

```python
prefix = norm_title(group.get("title"))[:36]
```

`norm_title` 负责剥掉 `+9` / `通过广告销售更多` / `竞选中通过广告销售更多` 这些角标。
不剥的话，重载后角标一消失就找不到组了。

**② 轮询到子行出现后还要多等 1 秒**

`len(rows) > 1` 只说明行容器出现了，卡片可能还没挂上。
直接取快照会读到「行有了、campaigns 是空数组」的中间态，导致这个商品被判定为
「没有任何活动」——**静默漏掉**。

## 代价核算

| 项 | 数值 |
|---|---|
| 单个组展开耗时 | 13s（reload）+ 4~8s（等子行）≈ **17~21s** |
| 单页带箭头的组 | 10~20 个 |
| 单页展开开销 | **3~7 分钟** |
| 两店 × 2~3 页 | **15~30 分钟** |

这就是「全量真实跑 20～35 分钟」的主要构成。**它无法优化到分钟级**，
除非平台改变这个行为。

## 对排障的影响

看到这条日志不要立刻当成故障：

```
第1次展开 gi22 未出子行，重试
```

它是**正常重试**。真正需要关注的是连续 3 次都失败：

```
第1次展开 gi24 未出子行，重试
第2次展开 gi24 未出子行，重试
第3次展开 gi24 未出子行，重试
[warn] gi24 展开失败，本组跳过
```

含义是这个组在这一轮**整个被跳过**，它下面的所有提案都没被判断。
实战记录里出现过这种情况（`Caixa Transporte Pet Gato Cach`），
同一轮第 2 页的同名组展开成功了——说明是偶发的页面卡顿，不是组本身的问题。

**处理策略：接受它，记账，下一轮会重新处理。** 不要为它加大重试次数——
每多一次重试就是多一次 13s 的 reload，而成功率并没有提升。

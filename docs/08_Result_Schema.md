# 08 · 结果 JSON 结构

结果文件：`tmp/auto_join_promos.json`
Schema：`schema/result.schema.json`

## ⚠️ 三条使用纪律

### 1. 每轮覆盖，跑前必须备份

结果文件是**单文件覆盖写**，不是追加。

```python
RESULT_PATH = os.path.join(BASE_DIR, "tmp", "auto_join_promos.json")
```

`main.py` 在启动时会自动备份上一轮：

```python
def backup_previous_result():
    # 读旧文件的 ts，用「旧文件的 ts」做备份名
    old_ts = old["ts"].replace(":", "").replace(" ", "_")
    dst = RESULT_PATH.replace(".json", "_%s.bak.json" % old_ts)
```

**备份名用的是上一轮内部记录的时间，不是当前时间。**
这一点很重要——见下面的事故记录。

### 2. 绝不用 `--dry` 做复核

**`--dry` 同样会覆盖结果 JSON。**

它只是不点按钮，但最后的写文件逻辑完全一样。

### 3. 🔴 事故记录（2026-10-14）

那天的真实经过：

1. 正常跑完，结果写入 `auto_join_promos.json`（ts = 10-14 01:2x）；
2. 为了排查 10 店「0 条」，追加跑了 `--store 10店 --dry`；
   → **空跑把结果文件覆盖成了 dry 版的 10 店数据**；
3. 发现不对，从备份恢复。但拿的备份文件是「跑前备份」，
   而它实际上是更早一轮（10-13）的文件；
4. 结果：**10-14 这一轮的完整结果永久丢失**。

三条教训：

- 排查一律先 `cp` 当前结果到带时间戳的新备份，**并核对备份里的 ts 确实是上一轮**；
- 绝不用 `--dry` 做复核；
- 复盘优先读 stdout 日志（日志是追加的，不会丢）。

## 顶层结构

```json
{
  "ts": "2026-10-17 01:25:11",
  "dry": false,
  "stores": ["4店", "10店"],
  "elapsed_seconds": 1327.4,
  "summary": { "4店": {...}, "10店": {...} },
  "results": [ ... ]
}
```

| 字段 | 说明 |
|---|---|
| `ts` | 本轮**写入**时间。备份文件名用它，所以必须是本轮时间 |
| `dry` | 是否空跑 |
| `elapsed_seconds` | 总耗时。两店正常 1200~2100 |
| `summary` | 按店铺汇总，直接可读 |
| `results` | 扁平记录列表，四种 type 混排 |

## results 的四种 type

| type | 含义 | 是否点了按钮 |
|---|---|---|
| `跳过` | 判定阶段就排除了，或弹窗复核时取消 | ❌ / ✅（开了弹窗又取消） |
| `可参加` | dry 模式下的候选 | ❌ |
| `参加` | 真实执行过的动作 | ✅ |
| `异常` | 页面级故障：掉登录、展开失败 | ❌ |

注意 `跳过` 有两种来源：

- **判定跳过**：只有 `reason`，没有 `result`；
- **弹窗复核取消**：有 `result="跳过"` 和 `detail`，说明按钮点过、弹窗开过、最后取消了。

区分方法是看有没有 `result` 字段。

## 跳过原因取值表

| reason | 含义 | 往轮量级 |
|---|---|---|
| `无绿字` | 卡片没有手续费减免绿字 | 66~143 |
| `无激活在跑活动` | 硬门槛：这个链接没有在跑的促销 | 19~40 |
| `净收不高于基准(基线X)` | join 侧卡片层预筛未通过 | 12~22 |
| `基准净收未解析(基线缺失)` | 激活/已预约卡片的净收都读不出来 | 罕见 |
| `有箭头但无 SKU 子链接行（父行忽略）` | 展开后只有聚合父行 | 少见 |

「无绿字」永远是大头。如果你看到它突然变成 0，先怀疑是**平台改文案了**
（见 [10_Troubleshooting.md](10_Troubleshooting.md) 的「关键词失效」一节）。

展开失败等下一轮自然恢复。

## 关键诊断字段

### `net_src` —— 读数可信度

| 值 | 可信度 | 含义 |
|---|---|---|
| `structured_pair` | ✅ 高 | 弹窗给了 ≥2 列，直接读 |
| `structured_single` | ✅ 高 | 只有 1 列，当前值取自卡片读数 |
| `modal_pair` / `modal_single` | ✅ 高 | join 侧的弹窗复核 |
| `flat_fallback` | ⚠️ **低** | 结构化读取失败，退回拍平文本取数 |
| `none` | ❌ | 全读不到（此时应该已取消） |

**`flat_fallback` 出现时要人工抽查。** 这个路径的读数可能把手续费减免额当成净收。

### `bi_orig` / `btn_locate` —— 索引是否失效

`bi_orig` 出现说明发生过 DOM 重排、原索引失效、走了扫描兜底。

`btn_locate` 的值：

- `scan_sig`：按卡片文本签名命中 ✅
- `scan_first`：签名没对上，退到「第一个可点按钮」 ⚠️ **这条要人工看**

### `qty_default` —— 数量是否兜底

`true` 表示读不到仓库数量、保持了平台默认值。正常情况，不用管。

### `net_cells` —— 弹窗原始文本

排障利器。当怀疑读数不对时，直接看这个：

```json
"net_cells": ["R$ 1.239,70包含 R$ 57,29 的销售佣金减免。"]
```

一眼就能看出 57,29 是手续费减免额，不是净收。

## summary 示例

```json
"4店": {
  "可参加/参加": 17,
  "跳过": 134,
  "异常": 0,
  "成功": 6,
  "失败": 2,
  "待核验": 0,
  "净收不达标取消": 9,
  "跳过原因Top": {
    "无绿字": 97,
    "无激活在跑活动": 23,
    "净收不高于基准(基线38.83)": 14
  }
}
```

换算关系：

```
参加 = 成功 + 失败 + 待核验 + 净收不达标取消
```

如果对不上，说明有记录的 `result` 值不在预期集合里——查 `detail`。

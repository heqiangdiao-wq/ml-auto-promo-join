# 12 · 合规边界与不做什么

## 一、这个项目只做一件事

**在卖家中心已有的促销提案里，按你自己的既定规则挑选并参加。**

它不做：

- ❌ 不创建活动、不改价格、不上架商品
- ❌ 不碰广告（限时抢购弹窗里的「通过广告触达更多买家」复选框永远不勾）
- ❌ 不操纵评价、不刷单、不做任何违反平台规则的动作
- ❌ 不绕过登录验证、不破解验证码、不伪造请求

所有动作都等价于**运营本人在卖家中心页面上手动点击**——
用的是同一个浏览器、同一个登录态、同一套平台 UI。
区别只是：人一天看 300 条提案会疲劳，脚本不会。

## 二、所有保护性设计的默认方向

判断不确定时，这个项目一律选**「不做」**。

| 情况 | 处理 | 理由 |
|---|---|---|
| 基准净收读不出来 | 跳过 + 记账 | 没有基准就没有判断依据 |
| 弹窗净收读不出来 | 取消 | 宁可放弃，不在数字不可信时点确认 |
| 确认按钮 disabled | 取消 | 平台在拦，不硬试 |
| 仓库数量读不到 | 保持平台默认 | 不猜，不兜底填 1 |
| 手续费减免绿字没有 | 跳过 | 少一层平台让利 |
| 无激活在跑 | 整链接跳过 | 没有基准，等于凭空降价 |
| 店铺掉登录 | 报警 + 跳过 | 不尝试绕过登录 |

**没有一处是「猜一个值然后继续」。** 这是有意的。

## 三、关于「净收更高才参加」这条规则的性质

这条规则的本质不是「赚更多」，而是「在平台给的选项里择优」。

它有一个显而易见的推论：**如果平台给的提案全都不如现状，一条都不会参加。**
实战数据也印证了这点——单轮 137～347 条记录里只参加 3～9 条。

这是正确行为，不是"脚本不够努力"。

## 四、数据与隐私

### 仓库里有什么

- ✅ 全部代码
- ✅ 全部文档与实战复盘（含脱敏后的金额与量级）
- ✅ 结果 JSON 的结构样例（`samples/example_result.json`，标识全部为 `DEMO-*`）

### 仓库里没有什么

- ❌ **真实 storeId** —— 配置走 `config/stores.local.json`，已被 `.gitignore` 排除
- ❌ **Cookie / 登录凭据 / token** —— 这个项目完全不接触这些（登录态由紫鸟客户端管理）
- ❌ **真实结果数据** —— `tmp/` 与 `logs/` 都被排除
- ❌ **真实 SKU 与商品标题** —— 样例中全部替换为 `DEMO-*`

### 注意：文档里的真实数据

`docs/11_Run_Journal.md` 里保留了真实的**金额量级、条数、日期与故障现象**，
但商品标识都做了泛化处理。

如果你 fork 这个项目用于自己的店铺，**注意你自己的结果 JSON 里会包含
真实 SKU 与 MLB**。别把 `tmp/` 提交上去——`.gitignore` 已经排除了，
但用 `git add -f` 强推时会绕过它。

## 五、使用前提与责任

1. **你需要自己拥有或有权操作这些店铺。** 这个项目不提供任何账号。
2. **平台规则会变。** 所有选择器、文案判据、交互行为都是编写时的实测值。
   上线前、以及每隔一段时间，都应该跑 `--dry` 复核一次。
3. **净收规则你自己定。** 项目默认实现的是「打得过激活∪已预约里最差的那条」。
   这是一个合理的默认，但不必然是适合你的规则。改之前读
   [06_Decision_Rules.md](06_Decision_Rules.md)。
4. **首次真实运行前必须 `--dry`。** 确认能读到活动列表、判定结果量级正常，
   再放开真实参加。

## 六、这个项目不提供的保证

- 不保证平台不会改版
- 不保证净收读数永远正确（有兜底路径，但兜底的可靠性低于主路径）
- 不保证每个提案都被处理（展开失败会整组跳过，下一轮再处理）
- 不保证掉登录能自动恢复（不能，需要人工）

这些限制都写在对应的文档里，并且在结果 JSON 里以 `异常` / `待核验` 的形式显式记录。
**不会静默假装成功。**

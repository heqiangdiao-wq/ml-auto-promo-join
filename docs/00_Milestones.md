# 里程碑划分：4 个四分之一节点

本项目按 **20 个部分**逐段构建，再归并为 **4 个里程碑**。
划分不是按文件数硬切，而是按**依赖链的可用性边界**切——每个节点结束时，项目都刚好跨过一道「能单独验证」的门槛。

```
M1 打地基 ──→ M2 取数 ──→ M3 判定与执行 ──→ M4 工程化交付
   01-05        06-10          11-15              16-20
  11 文件       +8 文件        +7 文件            +10 文件
```

| 节点 | 覆盖部分 | Tag | 累计文件 | 结束时能做什么 |
|---|---|---|---|---|
| **1/4** | 01-05 | `q1-foundation` | 11 | 连上紫鸟浏览器，列出店铺，确认环境可用 |
| **2/4** | 06-10 | `q2-capture` | 19 | 打开推广中心、翻页到底、展开商品组拿到全部子链接 |
| **3/4** | 11-15 | `q3-decide-execute` | 26 | `--dry` 跑出完整判定结果；去掉 `--dry` 即真实参加 |
| **4/4** | 16-20 | `q4-deliver` | 36 | 结果有 Schema 约束，他人可照文档独立复现 |

---

## 1/4 · 打地基（part 01-05）

**目标**：证明「这台机器能操纵这个店铺」。

| 部分 | 内容 |
|---|---|
| 01 | 项目骨架与定位：README / .gitignore / LICENSE / 店铺配置模板 |
| 02 | 业务背景：美客多「报活动」在做什么，六条规则与三个边界 |
| 03 | 系统架构：分层、数据流、三条贯穿全局的约束 |
| 04 | 环境与依赖：紫鸟 CLI、storeId、四个环境坑 |
| 05 | CDP 客户端层：ziniao-cli 子进程封装与 exe 三级定位 |

**新增文件**：`README.md`、`.gitignore`、`LICENSE`、`config/stores.example.json`、`docs/01-03`、`src/__init__.py`、`src/constants.py`、`src/cdp_client.py`、`requirements.txt`

**验收标准**：能通过 `ziniao-cli` 拿到可用店铺列表；exe 定位在 PATH 缺失时仍能找到。

**这一段的坑**：CDP 客户端是全部后续代码的地基，exe 三级定位（环境变量 → PATH → 常见安装路径）如果只做一级，换台机器就全线瘫痪。

## 2/4 · 取数（part 06-10）

**目标**：把页面上「有哪些活动可以报」完整、无遗漏地读出来。

| 部分 | 内容 |
|---|---|
| 06 | 店铺会话层：exec_js / visit / click / 掉登录检测 |
| 07 | 纯函数工具：巴西金额解析、绿字检测、标题归一、去重键 |
| 08 | MLB → SKU 映射层 |
| 09 | 页面探测与分页：整页快照、末页号、越界页陷阱 |
| 10 | 商品组展开：一次页面加载只能展开一次 |

**新增文件**：`src/lt_common.py`、`src/utils.py`、`src/sku_map.py`、`src/js_snippets.py`、`src/page_probe.py`、`src/group_expand.py`、`docs/04-05`

**验收标准**：任意一个店铺，能把全部子链接及其活动卡片数量枚举出来，且数量与人工核对一致。

**这一段的坑**：业务里最贵的两个陷阱都在这里——分页末页号读错会少读一整页；「一次页面加载只能展开一次」如果违反，第二次展开会静默返回空，表现成「这个链接没有活动」，直接漏单。

## 3/4 · 判定与执行（part 11-15）

**目标**：从「读到了什么」走到「该不该点、点了成不成」。

| 部分 | 内容 |
|---|---|
| 11 | 决策引擎：三条件判定与基准池模型 |
| 12 | 弹窗净收结构化读取：cols-3 与 cols-1 陷阱 |
| 13 | 执行器：三层定位兜底、弹窗复核、限时抢购数量 |
| 14 | 回执校验：snackbar 三种语义与重试边界 |
| 15 | 编排层：分店串行、分页循环、异常记录、结果落库 |

**新增文件**：`src/analyze.py`、`src/modal_reader.py`、`src/joiner.py`、`src/receipt.py`、`src/main.py`、`docs/06-07`

**验收标准**：`python -m src.main --dry` 能产出完整判定记录，且每条跳过/参加的理由都可追溯。

**这一段的分界线**：到 part 15 结束，项目已经是**可用**的——`--dry` 是只读模式，去掉即真实操作。part 16-20 不改变行为，只让它可交付。

**目标**：让第二个人（或三个月后的自己）能不靠口头解释把它跑起来。

| 部分 | 内容 |
|---|---|

| 18 | 排障手册：掉登录轮换、展开失败、索引失效、关键词失效 |

**新增文件**：`schema/result.schema.json`、`docs/08-12`、`run.sh`、`run.bat`、`samples/example_result.json`、`CHANGELOG.md`

**验收标准**：结果文件能通过 Schema 校验；排障手册覆盖实际遇到过的全部失败模式。

**这一段的坑**：排障手册的价值全部来自真实运行记录。凭想象写的排障条目在实际掉登录、索引失效面前一条都用不上。

## 为什么是这 4 个切点

不是按时长、也不是按文件数均分，而是三个「可用性跃迁点」：

1. **M1 → M2**：从「环境通了」到「能读到数据」
2. **M2 → M3**：从「读到数据」到「能做决策」——这是唯一一次质变
3. **M3 → M4**：从「能跑」到「能交付」——行为不再变化，只加护栏

反过来看，任何一段单独拿出去都没有独立价值：只有 M2 没有 M3，是一堆读取器；只有 M3 没有 M2，决策引擎没有输入。四段串起来才是一条完整的业务闭环。
